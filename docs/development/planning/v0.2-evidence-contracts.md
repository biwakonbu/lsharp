## 目指すもの

L# v0.2 は、仕様を「正しいと証明する」だけの言語ではなく、**誤った仕様が開発中に自己整合したまま残りにくい executable contract language** を目指す。

人間の意図から仕様を得る過程には、観測漏れ、前提の誤り、反例不足、レビューの独立性不足が残る。実装と仕様が完全に一致していても、仕様そのものが意図を取り違えていれば利用者にとって正しくない。L# はこの不確実性を隠さず、次の情報を first-class に扱う。

- intent: 誰のどの目的を満たすのか
- claim: 何が真だと主張しているのか
- assumption: 主張が依存する前提
- open question: 未決定または未検証の問い
- case / property: 実行可能な正例、反例、一般化した性質
- observation: 実行、production、reference implementation から得た観測
- review: 誰が、どの独立性で、何を確認したか
- provenance: evidence の生成元、時刻、tool、version、seed
- invalidation: 変更によってどの主張・レビュー・証跡が古くなったか

## Assurance の二軸

L# は assurance を単一の `verified` 状態へ畳み込まない。

### Implementation conformance

実装が明示された executable contract を満たすかを示す。

- example/case/assert/property の実行結果
- 使用した runner と target
- case 数、seed、generator、shrink 結果
- coverage と未到達 branch
- Rust oracle と selfhost の差分

### Intent validation

contract が stakeholder intent と利用環境を十分に表しているかを示す。

- intent と claim の追跡可能性
- assumption と open question の残数
- positive/negative/discriminating case の有無
- production/reference observation との整合
- review の provenance と独立性
- semantic change 後に失効した evidence

両軸の片方が成功しても、もう片方を成功扱いにしない。たとえば「全 property が通るが stakeholder review がない」は conformance success / intent unknown であり、overall verified ではない。

## 現行実装で確認できた問題

2026-07-17 時点の current source には次の不一致がある。これは v0.2 の出発点であり、現行挙動を完成仕様として追認しない。

| 境界 | 現状 | 問題 |
|---|---|---|
| Rust metadata checker | `:example` の Int 式を許容し、invariant/example 内の元関数引数参照を許容 | runner が同じ scope/type を実現しない |
| Rust runner | example は通常 compiler pipeline の `if` に入るため Bool 必須 | checker と不一致 |
| selfhost runner | example は 0/非0 truthiness | Rust runner と不一致 |
| invariant sampling | 1引数は `0,1,5,-1,42`、2引数以上は先頭2引数の 3×3、残りは 0 | method/coverage が利用者向け結果に十分露出しない |
| invariant scope | 関数呼び出しには引数を bind するが contract 式には `result` だけを bind | checker が許可した元引数参照を実行できない |
| selfhost parser | doc/example/params/returns の一部だけを独自 shape で保持し invariant は保持しない | canonical metadata IR がない |
| constraint generator | integer boundary helper はあるが metadata runner へ未接続 | docs が示唆する random/boundary testing と実挙動が一致しない |

一次ソースは `crates/lsharp-types/src/metadata_check.rs`、`crates/lsharp-wasm/src/test_runner.rs`、`crates/lsharp-tooling/src/metadata_test.rs`、`selfhost/src/Syntax/Parser.ls`、`selfhost/src/Tools/Test/TestRunner.ls`、`crates/lsharp-types/src/constraints.rs` とする。

## v0.2 contract surface

### 役割の分離

現行の曖昧な `:example` / `:invariant` を、次の概念へ分離する。

```lisp
(defn abs [x]
  :doc "絶対値を返す"

  ; 説明用。表示・docs 生成に使い、pass/fail を持たない。
  :example [(abs -5)]

  ; 入出力または期待診断を明示した具体例。
  :case [(expect (abs -5) 5)
         (expect (abs 0) 0)]

  ; 定義時に型検査する Bool assertion。
  :assert [(>= (abs -5) 0)]

  ; generator と全パラメータ scope を持つ sampled property。
  :property [(for-all [x Int]
               :postcondition (>= result 0))]

  (if (< x 0) (- 0 x) x))
```

初期 syntax は上記を設計基準とする。parser 実装前に canonical metadata IR と migration fixture で最終 shape を固定する。

### 意味論

| form | 型 | scope | 実行 | 主な出力 |
|---|---|---|---|---|
| `:example` | 任意 | lexical scope のみ | pass/fail なし | rendered value/source |
| `:case` | `Expectation` | 明示入力のみ | 各 case 1 回 | expected/actual/diagnostic |
| `:assert` | `Bool` | lexical scope のみ | deterministic | pass/fail |
| `:property` | `Bool` postcondition | 全 generated parameters + `result` | sampled | seed/cases/shrinks/coverage |
| `:postcondition` | `Bool` | parameters + `result` | property/case に従う | predicate result |

- truthiness は contract 判定に使わない。
- 元関数引数を暗黙に参照できるのは property/postcondition とし、case は入力を明示する。
- unsupported feature は Unit/0 への silent fallback ではなく stable diagnostic を返す。
- zero case、到達不能 predicate、常に真の predicate は成功ではなく non-vacuity warning/error の対象にする。

### Canonical metadata IR

Rust parser、selfhost parser、formatter、checker、docs、runner は同じ概念モデルを共有する。

```text
ContractSuite
  owner: SymbolId
  docs: [Example]
  executable: [Case | Assertion | Property]
  intent_links: [IntentId]
  claim_links: [ClaimId]
  source_span: Span

Property
  binders: [Binder { name, type, generator }]
  preconditions: [Predicate]
  postcondition: Predicate
  sampling: SamplingPlan { cases, seed, shrink, coverage }
```

source text scan、raw text metadata、tag vector の三重管理を廃止し、各 surface は canonical IR の lossless projection にする。

## Evidence model

### 最小 graph

M2 では次の node/edge を導入する。

```text
Intent -> motivates -> Claim
Claim -> constrained-by -> Assumption
Claim -> tested-by -> Case | Property
Observation -> supports | contradicts -> Claim
Review -> evaluates -> Intent | Claim | Evidence
Change -> invalidates -> Review | Evidence
```

各 Evidence は最低でも次を持つ。

- `evidence_id`
- `method`: example/case/assert/property/production/reference/proof/review
- `subject`: claim または contract
- `outcome`: pass/fail/contradicted/unknown/stale
- `runner`, `target`, `source_commit`, `artifact_digest`
- `cases`, `seed`, `generator`, `shrinks`, `coverage`
- `provenance`: producer、tool version、timestamp
- `independence`: same-author / independent-review / external-observation

### Structured assurance report

```json
{
  "implementation_conformance": {
    "status": "pass",
    "method": "sampled-property",
    "cases": 256,
    "seed": 81042,
    "coverage": {"negative": 121, "zero": 1, "positive": 134}
  },
  "intent_validation": {
    "status": "unknown",
    "open_questions": 2,
    "independent_reviews": 0,
    "contradicting_observations": 0
  }
}
```

top-level `verified: true` は出力しない。consumer が policy を決められるよう、事実を lossless に返す。

## Command boundary

| command | 責務 | v0.2 の位置づけ |
|---|---|---|
| `lsharp test` | implementation conformance | case/assert/property を実行し、再現可能な report を返す |
| `lsharp validate` | intent/evidence validation | M2 で追加。trace gap、stale review、open question、evidence independence を報告 |
| `lsharp prove` | external proof backend | M5 候補。SMT/Lean 等の外部境界を明示 |

`test` の成功を stakeholder intent の妥当性へ読み替えない。`validate` も人間の意図を自動的に正しいと宣言せず、欠落・矛盾・provenance を可視化する。

## Generator と再現性

M1 の generator は次を満たす。

- 型指向: Int/Bool/String/ADT/record の generator を型から選ぶ
- constraint-aware: 解決済み constraint conjunction を満たす inside case と破る boundary case を区別する
- deterministic: case count と seed を report に固定する
- shrinkable: failure を最小入力へ縮小し、元 seed と shrink path を保存する
- observable: 実行した値の分類と coverage を report する
- portable: Rust oracle、selfhost、Mac Apple Silicon、Linux x86_64 で同じ plan と result schema を使う

現行固定サンプル `0,1,5,-1,42` は移行期の `legacy-deterministic-smoke` profile として明示し、property testing の一般性を主張しない。

## Migration

### v0.1 source の分類

- Bool を返す `:example` は機械変換候補として `:assert` を提案する。
- non-Bool `:example` は docs-only `:example` として保持し、test count に含めない。
- `:invariant` は scope と意図を解析し、`result`/parameters を参照するものは `:property ... :postcondition` への変換候補にする。
- 自動判定できない form は silent conversion せず stable migration diagnostic を返す。

### Compatibility window

1. v0.2 preview: legacy form を受理し、実際に選択した semantics と migration suggestion を report する。
2. v0.2 stable: ambiguous truthiness を拒否し、strict Bool と canonical scope を必須にする。
3. legacy profile: oracle/differential fixture のみで明示選択できる。通常 CLI の成功経路にはしない。

## Milestones

1. **M1 Honest executable contracts** — runner/checker/parser の不一致を閉じ、case/assert/property、reproducible sampling、二軸 report を実装する。
2. **M2 Intent and evidence graph** — intent/claim/assumption/question/evidence/review/provenance と `validate` を導入する。
3. **M3 Change-aware validation** — semantic diff、review invalidation、non-vacuity、reachability を導入する。
4. **M4 Adversarial evidence** — spec mutation、discriminating cases、production/reference differential を導入する。
5. **M5 External proof backends** — SMT/Lean 等を optional external boundary として接続する。

## 非目標

- 自然言語の要求から正しい仕様を自動生成したと宣言すること
- property test の成功を数学的証明と呼ぶこと
- Lean/SMT を導入するだけで intent validation が完了したと扱うこと
- Rust oracle の成功を selfhost/native parity の代替にすること
- unsupported target を v0.2 の完了条件へ追加すること

## 未決定事項

- `:property` と `:postcondition` を単一 form にするか nested form にするか
- intent/claim ID を source 内 symbol、project manifest、外部 tracker のどこで発行するか
- intent validation failure を command exit code にどう写像するか
- production observation の privacy/redaction policy
- proof backend の evidence independence をどの level で表すか

未決定事項は M1 の parser 実装を止めない範囲で ADR または milestone task に分離する。
