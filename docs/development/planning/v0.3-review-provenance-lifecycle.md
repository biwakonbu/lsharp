## 現在の実装状態（2026-07-31）

設計は提案段階から実装段階へ移行している。Rust canonical model の verified partial slice は
ADR と focused/integration test で固定済みだが、これを source/selfhost/native の parity や release
artifact の完了証拠へ拡大解釈しない。

- **EC-M3-01**: `ReviewAttestation`、strict UTC timestamp、length-prefixed UTF-8 canonical bytes、
  Ed25519 allowlist、explicit trust store、subject/source/provenance binding、explicit clock による
  expiry/lifecycle 判定を Rust 側で検証済み。代表 ADR:
  [`decisions-v0.3-review-signature-verification.md`](../../adr/decisions-v0.3-review-signature-verification.md)、
  [`decisions-v0.3-review-lifecycle-clock-state.md`](../../adr/decisions-v0.3-review-lifecycle-clock-state.md)。
- **EC-M3-02**: append-only lifecycle reducer、`(review_id, sequence)` の deterministic ordering、
  許可された state transition、sequence/effective time rollback の fail-closed、clock 時点の
  `event_at` 選択を Rust で検証済み。provider snapshot と report/native parity は未完了。
- **EC-M3-03**: CLI/MCP の trust store、lifecycle、subject/source/clock context は explicit input
  boundary として Rust host で検証済み。selfhost/native MCP と target artifact parity は未完了。
- **EC-M3-04 / EC-M3-05**: source/selfhost/native producer の同一 fixture、current-source provenance、
  Mac Apple Silicon / Linux x86_64 の packaged stage0/runtime gate、release/evidence projection は
  次の未完タスクである。release identityについては、explicit digest objectを offlineで検証する
  [`decisions-v0.3-release-identity-gate.md`](../../adr/decisions-v0.3-release-identity-gate.md) の
  verified partial sliceを追加した。通常の selfhost `App.Cli` の explicit identity JSON/text/manifest
  projection も Rust-host actual Wasm で追加検証したが、provider adapter と current-source target
  runtimeは未接続である。

次の実行単位と validation gate は
[`v0.3-milestone-01.md`](v0.3-milestone-01.md) に固定する。M3-04-N1 の current-source native
source-file parity を先に閉じ、続いて M3-05-N1/N2 の evidence identity と release gate を進める。

ここでいう verified partial は、canonical Rust oracle の境界が固定されたという意味であり、
「Rust なしで全 surface が動く」または「v0.3 がリリース可能」という意味ではない。

## 目的

M2 では review を `ReviewId`、opaque な `provenance_digest`、
`public` / `redacted` の visibility として扱う。これで個人情報を manifest へ漏らさずに
review の存在と edge closure を保持できるが、digest が誰によって発行されたか、対象の
manifest に対する review か、後から失効していないかは判定できない。

v0.3 では、review の本文や reviewer の個人情報を L# の wire に持ち込まず、
「何に対する review を、どの鍵で、いつ、どの lifecycle 状態で認証したか」を検証可能な
attestation として扱う。検証できない review は graph から捨てず `unverified` として保持するが、
独立 review gate や `status: pass` の根拠には数えない。

この文書は provider API の統合を先に実装するものではない。Rust canonical model、CLI/MCP、
selfhost/native の各境界が同じ observable contract を共有できるよう、入力、検証状態、
lifecycle、失敗境界、段階的な実装タスクを先に固定する。

## 現状の境界

M2 の現行契約は次のとおりである。

- `reviews` は optional registry で、`ReviewId`、opaque `provenance_digest`、visibility だけを持つ。
- author、email、body、URL、token、署名 material は manifest に投影しない。
- registry が明示された場合、`evaluates` / `invalidates` の review endpoint は登録済み ID に閉じる。
- provider authentication、digest の暗号学的検証、外部 lifecycle、native stage0 parity は未完了である。
- registry がない既存 manifest は external `ReviewId` として後方互換に受理する。

v0.3 はこの境界を置き換えず、attestation の検証結果を registry record の追加情報として
明示する。既存 manifest の意味を暗黙に `verified` へ昇格させない。

## 設計原則

1. **内容ではなく証明を持つ** — review 本文・個人情報は外部 provider に残し、L# は対象 digest と署名だけを扱う。
2. **対象を署名する** — review ID だけでなく、対象 manifest/graph と source commit の digest を署名対象に含める。
3. **不確実性を保持する** — 未検証、期限切れ、失効、鍵不明を同じ `pass` に畳み込まない。
4. **append-only lifecycle** — review の状態変更は履歴として追加し、既存 record を破壊的に書き換えない。
5. **offline deterministic** — CLI と native stage0 の成功経路は network に依存せず、明示的に渡された keyset と lifecycle snapshot だけで検証する。
6. **privacy by construction** — public artifact に出す field を schema で allowlist 化し、provider の opaque payload をそのまま通さない。
7. **Rust/selfhost parity** — Rust が canonical oracle であり、selfhost/native は同じ canonical bytes、状態遷移、診断を投影する。

## v0.3 の wire model

### Attestation envelope

既存 `ReviewRecord` は維持し、attestation を optional に追加する。概念上の version 1
shape は次のとおりとする。

```json
{
  "review_id": "review:checkout/reviewer-001",
  "subject_digest": "sha256:...",
  "source_commit": "0123456789abcdef...",
  "provenance_digest": "sha256:...",
  "provider": "github",
  "key_id": "org/reviews-2026",
  "algorithm": "ed25519",
  "signature": "base64url...",
  "issued_at": "2026-08-01T00:00:00Z",
  "expires_at": "2026-09-01T00:00:00Z",
  "sequence": 3
}
```

`subject_digest` は review が評価した canonical graph/manifest の digest である。
`source_commit` は current checkout の provenance であり、manifest の別 commit への
再利用を防ぐ。`provenance_digest` は既存 opaque registry と同じ値を指し、署名の対象にも
含める。`provider` と `key_id` は鍵解決の識別子であり、reviewer の個人情報ではない。

provider ごとの JSON を直接署名対象にしない。cross-target の canonical bytes は field order を
固定した length-prefixed UTF-8 record とし、概念的には次の順序で encode する。

```text
lsharp.review-attestation.v1\0
review_id\0 subject_digest\0 source_commit\0 provenance_digest\0
provider\0 key_id\0 algorithm\0 issued_at\0 expires_at\0 sequence\0
```

各 field は UTF-8 byte length と bytes を持ち、optional `expires_at` は空 field として
表現する。`sequence` は unsigned decimal を canonical にする。実装ではこの encoding を
Rust の unit test で先に固定し、selfhost/native は同じ fixture の bytes と digest を比較する。
JSON の key 順、locale、時刻の表示形式、Rust の hash seed に依存させない。

### Lifecycle record

attestation の検証と lifecycle は別の事実として保持する。provider snapshot または
明示 lifecycle input は append-only event として扱う。

```json
{
  "review_id": "review:checkout/reviewer-001",
  "sequence": 4,
  "state": "revoked",
  "effective_at": "2026-08-10T12:00:00Z",
  "reason_digest": "sha256:..."
}
```

許可する遷移は次のとおりとする。

```text
proposed -> active -> superseded
                   \-> revoked
```

`revoked` と `superseded` から `active` へ戻すことはできない。新しい署名対象へ戻す
場合は別の `sequence` と attestation を発行する。sequence の重複、逆行、同一 sequence
で異なる payload、過去へ戻る遷移は fail-closed に拒否する。

### Verification state

検証結果は graph の fact として一つだけ投影する。

| state | 条件 | independent review gate |
| --- | --- | --- |
| `verified` | 署名、信頼鍵、対象 digest、source commit、時刻、lifecycle が一致 | 数える |
| `unverified` | attestation がない、または鍵が明示されていない | 数えない |
| `stale` | `expires_at` 超過、対象 digest/source commit 不一致、active でない | 数えない |
| `revoked` | lifecycle が revoked | 数えない |
| `invalid` | wire、canonical bytes、署名、sequence の検証に失敗 | 入力診断として停止 |

`invalid` は report の `unknown` と混ぜず、parse/verification error として report/manifest
を生成しない既存 fail-closed policy を維持する。`unverified` / `stale` / `revoked` は
manifest に状態を残せるが、validation report は `unknown` へ遷移する。

## 鍵と provider の境界

- compiler/runtime は provider network API を呼ばない。
- CLI は既存 semantic contract system と同じ `--trust-store <file>` と
  `--review-lifecycle <file>` の明示入力だけを読む。
- MCP は同じ schema の `trust_store` / `review_lifecycle` input を受けるが、remote fetch は
  caller の責務とし、tool 自身は取得しない。
- native stage0 は keyset と lifecycle snapshot の digest を manifest provenance に含める。
- trusted key の allowlist は project/release policy で渡し、manifest が自分自身で trust root を
  宣言して検証を完結させることは許さない。
- `algorithm` は allowlist にない値を `unsupported` ではなく入力エラーとして扱い、暗黙の
  fallback（別アルゴリズム、Rust host、network helper）を行わない。

この境界により、同じ manifest と keyset を Mac Apple Silicon、Linux x86_64、Rust oracle、
selfhost/native で実行したとき、verification state が一致する。provider の取得タイミング
による非決定性は実行前の snapshot 作成時に閉じる。

## 実装タスク

各タスクは `RED → canonical GREEN → Rust differential → native stage0 → docs` の順で進め、
未接続の surface は `[~]` として残す。既存 M2 の source/native smoke script と同じファイルを
変更するタスクは、active branch の merge 後に着手する。

### EC-M3-01 — canonical bytes と attestation model

- RED: empty field、非 canonical timestamp、unknown algorithm、invalid base64、sequence overflow を固定する。
- `ReviewAttestation`、`ReviewVerificationState`、canonical bytes、digest/signature verifier を Rust に追加する。
- `ReviewRecord` との optional projection と既存 `reviews` bytes の後方互換を確認する。
- 同一 fixture の canonical bytes/digest を Rust と selfhost で byte-for-byte 比較する。

完了条件は署名ライブラリの unit test だけではなく、対象 digest/source commit の mismatch が
`stale`、wire/署名破損が入力診断になることまで含む。

### EC-M3-02 — lifecycle transition validator

- RED: duplicate sequence、sequence rollback、revoked→active、同一 sequence の payload 差し替えを固定する。
- append-only event registry と deterministic state reducer を実装する。
- declaration order ではなく `(review_id, sequence)` でソートし、同じ入力の状態を target 間で一致させる。
- stale/revoked を M2 report の `stale_reviews` と `unknown` policy へ接続する。

### EC-M3-03 — CLI/MCP explicit inputs

- `validate` に keyset/lifecycle の明示入力を追加し、path traversal、project root 外、duplicate key、unknown field を拒否する。
- `lsharp_validate` MCP schema に同じ input/output shape を追加する。
- network、環境変数、implicit default keyset を成功経路から遮断する contract test を置く。
- verification error は no-report/no-manifest、stale は report を残して `unknown` という境界を固定する。

### EC-M3-04 — source と selfhost/native producer parity

- source の既存 `:review` は互換維持し、attestation は named fields の明示 form だけを受理する。
- Rust source adapter、selfhost `IntentSource` / `Evidence`、native source-file smoke の三者で
  canonical bytes、state、span、exit code を同じ fixture にする。
- trust store/lifecycle を source に埋め込まず、manifest-side input との二重指定を拒否する。
- current-source provenance と packaged stage0 artifact の一致を Mac/Linux で検証する。

### EC-M3-05 — release/evidence gate

- keyset digest、lifecycle snapshot digest、source commit、artifact digest を evidence identity に記録する。
- verified/unverified/stale/revoked/invalid の各状態を JSON/text/MCP で同じ順序に投影する。
- provider integration は外部 helper boundary として明示し、helper 不在時に verified と誤認しない。
- ADR、schema、guide、TODO を evidence と同時に更新し、完了した slice の履歴は TODO から ADR へ移す。

## 移行と互換性

1. M2 の `reviews` registry だけを持つ manifest は `unverified` として受理する。
2. attestation がある場合も、対象 digest/source commit がない旧 manifest は `stale` とする。
3. `public` / `redacted` の privacy semantics は変更しない。署名は privacy の代替ではない。
4. 既存の `independent-review` evidence は、M3 verifier が `verified` を返すまで gate の対象外になる。
5. 旧 consumer が attestation field を知らない場合は unknown-field error にせず、version negotiation
   で明示的に `v1` を選んだときだけ受理する。暗黙の部分読み取りは行わない。

## 決定済みの v0.3 初版 boundary

- 署名 algorithm は `ed25519` だけを allowlist し、unknown algorithm や implicit fallback は入力エラーにする。
- canonical bytes は固定 field order の length-prefixed UTF-8 とし、JSON key order や locale に依存させない。
- verification state は `verified` / `unverified` / `stale` / `revoked` / `invalid` を区別し、
  `verified` だけを independent review gate の根拠にする。
- provider network access は compiler/runtime の成功経路へ入れず、trust store/lifecycle snapshot は
  caller が明示的に渡す。

- key rotation と複数 provider の同一 review ID を許すか。
- current-source provenance と packaged stage0 artifact の release policy をどの manifest digestへ
  投影するか。
