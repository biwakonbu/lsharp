# 差分判定規則 (Gap Classification)

Phase 11 の監査において、Rust 実装と L# 実装の差分を以下の 5 種に分類する。

## 差分分類

### 1. 仕様差分 (Specification Gap)

**定義**: TODO.md, README.md, book/ の記述と実装の間に不一致がある状態。

**検出方法**:
- TODO.md の完了表示 (`[x]`) とコード・テストの実在を突合
- README.md の導入手順を実行して再現性を確認
- book/ の説明と現行パイプラインの動作を比較

**判定基準**:
- ドキュメントに記載された機能がコード上に存在しない -> 仕様差分
- コード上に存在するがドキュメントと異なる挙動を示す -> 仕様差分
- ドキュメントに記載されていないが実装されている -> 仕様差分 (ドキュメント不足)

**是正方針**: ドキュメントと実装の双方を確認し、正しい側に合わせる。曖昧な場合は ADR に判断根拠を記録する。

### 2. 実装欠落 (Implementation Gap)

**定義**: 仕様上必要とされるコードが存在しない状態。

**検出方法**:
- selfhost/*.ls の各モジュールについて、Rust 側の対応機能がカバーされているか確認
- compatibility-matrix.md の `L# status` が「なし」の項目を列挙
- 関数シグネチャが存在するが本体が未実装 (スタブ/TODO) の場合も含む

**判定基準**:
- 対応するソースファイルが存在しない -> 実装欠落
- ファイルは存在するが必要な関数・モジュールが不在 -> 実装欠落
- スタブのみで動作しない -> 実装欠落

**是正方針**: Phase 11 の後段タスク (P11-2 以降) で実装する。欠落の記録は compatibility-matrix.md で管理する。

### 3. 出力差分 (Output Gap)

**定義**: 同一入力に対して Rust 実装と L# 実装の出力が一致しない状態。

**検出方法**:
- E2E テストの期待値と実際の出力を比較
- golden test (snapshot test) の差分を検出
- `#[ignore]` 付きテストの内容を確認し、無視理由を記録

**判定基準**:
- テストが fail する -> 出力差分
- テストが `#[ignore]` で実行されていない -> 潜在的出力差分 (検証債務)
- テストが存在しない機能の出力 -> 実装欠落として扱う

**是正方針**: 出力差分は正しさの問題として優先的に解消する。テスト名と差分内容を記録する。

### 4. 性能差分 (Performance Gap)

**定義**: 機能は正しいが、実行速度・メモリ使用量・バイナリサイズに差がある状態。

**検出方法**:
- ベンチマーク (`scripts/bench-compare.sh`) で実行時間・メモリ使用量を比較
- バイナリサイズの比較 (`scripts/bench-wasm-size.sh`)
- peak RSS の測定

**判定基準**:
- 実行時間が 2x 以上遅い -> 性能差分 (要記録)
- メモリ使用量が 2x 以上大きい -> 性能差分 (要記録)
- バイナリサイズが 2x 以上大きい -> 性能差分 (要記録)

**是正方針**: Phase 11 の blocking 条件にしない。正しさ差分 (出力差分・実装欠落) を優先して解消する。性能差分は記録のみ行い、Phase 11 完了後の最適化フェーズで対処する。

### 5. 運用差分 (Operations Gap)

**定義**: 開発・配布・運用に関わるインフラ面の差分。

**対象範囲**:
- **CI**: GitHub Actions ワークフロー、テスト自動化、CI gate
- **配布**: リリースアーティファクト生成、アーカイブ形式、checksum
- **署名**: バイナリ署名、公証 (macOS notarization)
- **VSCode 連携**: 拡張パッケージング、LSP バイナリ同梱
- **インストール手順**: README/book の手順で実際にインストール・実行できるか

**検出方法**:
- `.github/workflows/` の設定と実際の CI 実行結果を照合
- `editors/vscode/` のパッケージ設定を確認
- README.md の Quick Start を実際に実行 (`scripts/smoke_test_readme.sh`)

**判定基準**:
- CI で L# 実装のテストが実行されていない -> 運用差分
- 配布物に L# バイナリが含まれていない -> 運用差分
- README の手順で実行できない -> 運用差分

**是正方針**: 運用差分は P11-6 (CI 切替と Rust 撤去) で段階的に解消する。

## 差分の優先順位

正しさを優先し、以下の順で解消する:

1. **仕様差分** -- ドキュメントと実装が不一致だと判断基盤が崩れる
2. **実装欠落** -- コードが存在しないと検証できない
3. **出力差分** -- 正しさの直接的な指標
4. **運用差分** -- 配布・CI は正しさ確認後に整備
5. **性能差分** -- 正しさ確定後に最適化

## 自動検出

`scripts/audit_docs.sh` で以下の差分を自動検出する:

- 仕様差分: TODO.md の `[x]` 項目にエビデンスが紐付いているか
- 実装欠落: selfhost/ の必須ファイルが存在するか
- 出力差分: `#[ignore]` 付きテストの数
- 運用差分: README の導入手順のコマンドが実行可能か
