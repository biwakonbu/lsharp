# TDD ワークフロー実行

実装タスクを TDD (テスト駆動開発) で進めるためのコマンド。

## 引数

$ARGUMENTS = 実装するタスクの説明 (例: "P6-3 Computation Expression の脱糖実装")

## ワークフロー

以下の手順を **基本的にこの順番で** 実行してください。

### Step 1: タスク分析
- 引数で指定されたタスクの内容を把握する
- TODO.md / docs/type-system-roadmap.md から対応する要件を確認する
- 変更対象のファイルを特定する

### Step 2: テスト設計
- テストケースを設計する (正常系 + 境界ケース + エラーケース)
- テスト名は `test_<機能>_<条件>` の形式にする
- テスト対象のモジュールの既存テストパターンを確認し、それに合わせる

### Step 3: テスト作成 (RED)
- テストコードを **先に** 書く
- テストは対象ファイルの `#[cfg(test)] mod tests` 内、または `tests/` ディレクトリに配置
- `cargo test -p <crate> -- <test_name>` でテストを実行し、 **失敗することを確認** する
- テストがコンパイルエラーになる場合は、`todo!()` マクロで関数シグネチャのみ定義してコンパイルを通し、「テスト失敗 (パニック)」状態にする
  ```rust
  // 例: まず関数シグネチャだけ定義
  fn desugar_computation(steps: &[ComputationStep]) -> Vec<Instruction> {
      todo!("bind/return への脱糖を実装")
  }
  ```

### Step 4: 実装 (GREEN)
- テストを通すための最小限の実装を書く
- `cargo test -p <crate> -- <test_name>` でテストを実行し、 **全て通ることを確認** する
- 通らないテストがある場合、実装を修正する (テストを修正しない)

### Step 5: リファクタリング (REFACTOR)
- 実装の品質を改善する (重複排除、命名改善等)
- `cargo test -p <crate>` で全テストが通ることを確認する

### Step 6: 全体テスト
- `cargo test` でプロジェクト全体のテストを実行する
- `cargo clippy` で警告がないことを確認する
- 既存テストを壊していないことを確認する

### Step 7: TODO 更新
- 対応する TODO.md の項目を `[x]` に更新する
- テスト数・テスト内容をコメントとして記載する (例: `-- ユニットテスト 5 個追加`)
- docs/type-system-roadmap.md に関連する記載があれば整合性を確認する

## 重要なルール

- **テストなしで `[x]` にしない**: テストが通った証拠がなければ完了と見なさない
- **テストを先に書く**: 実装ファイルの編集はテスト作成の後
- **テストを修正しない**: テストが失敗したら実装を直す。テストの期待値が間違っている場合のみテストを修正
- **最小限の実装**: テストを通すために必要な最小限のコードのみ書く

## 行き詰まり時の対処

- テスト失敗を3回修正しても解決しない場合: テストの設計を見直す
- コンパイルエラーが解消しない場合: `todo!()` で一旦スタブにし、別のアプローチを検討
- 現在のタスクが他の未実装機能に依存している場合: TODO.md に [BLOCKED] と記載して次のタスクへ移る
